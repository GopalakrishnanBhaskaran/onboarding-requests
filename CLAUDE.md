# CLAUDE.md — PMO onboarding flow (v2, Azure, low cost)

v2 (17 Oct 2026) replaces the Phase 1 readiness review and the Phase 2/2b/2c Entra hand-off. Flow: requester submits → **AI review** (mapping sheet + response document) → **Owner** approval → **Security** approval → **ID team** creates user/group (+ TAP) → **role assignment team** assigns roles → **AI verification** of the access (account, membership, exact roles; never waits for the user's sign-in, 22 Oct 2026), notifications, audit.
Notifications (22 Oct 2026, go-live): the Owner is mailed only to decide; the **requester** (who submitted the request) gets the one completion mail with Security, PMO, ID team and role assignment team; the joiner gets *access ready* at the Enterprise ID mail. Team addresses come from the **Contact inventory** page (semicolon-separated per team; PMO and Operators save it; versioned, changes mailed to Security and PMO; never decides who approves). Mail goes out within the sender's limit, most urgent first (`MailLimits`; ACS Azure-managed domain 5 a minute / 10 an hour, F70).
The **AI agent reviews, validates, summarises, routes, tracks, verifies and reports. It never approves.** v2.1 (Gokul, 17 Oct 2026; off until approved): only after both approvals the worker creates the user, group and membership and assigns allow-listed Azure roles. Agent TAP (Gokul, 22 Oct 2026; off until approved): for an account it has just created, the worker also mails the joiner a one-time TAP, the initial password and the MFA set-up steps, once; otherwise the TAP stays with the ID team. Agent privileged rows (Gokul, 22 Oct 2026; off until approved): rows flagged privileged are provisioned by the agent too, never the privileged administrator roles (F68).

Source of truth for scope: `SCOPE.md`. Platform facts: `docs/VERIFIED_FACTS.md`. **Open work and handoff: read `docs/NEXT_SESSION.md` first.** v1.1 feature pack (30 Oct 2026; option 1 live, agent offboarding Entra steps switched on): `PMO_Access_Portal_v1.1_Feature_Prompt.md`, decisions and plan `docs/V1_1_PLAN.md`, phase results `docs/V1_1_PHASES.md`, deploy runbook (P7 option 1) `docs/V1_1_DEPLOY.md`. ## Hard rules
1. **Cost.** Static Web Apps (Free) with managed Functions, Cosmos DB free tier, Azure Policy assignment, Cost Management budget, plus (approved 16 Oct 2026, Azure credits, budget ₹2,000/month, alerts 50/80/100%) one Flex Consumption Function App (the AI agent worker) and its one storage account with their role assignments — nothing else. Anything more needs Gokul's written approval.
2. **Never create:** Azure OpenAI, App Insights, Log Analytics, Key Vault, Service Bus, API Management, App Service (other than the Flex plan above), Azure SQL, VNets, private endpoints; no further Storage accounts or Function Apps. Azure OpenAI and mail/ADO adapters are coded and **off** until Gokul approves them. Mail (21 Oct 2026): one Azure Communication Services + one Email Communication Service (Azure-managed domain) via `tools/deploy_free.sh email` — coded, **off until approved** (dry run first).
3. **Verify, don't assume.** Check every limit, endpoint and permission against current Microsoft Learn; record URL + date in `docs/VERIFIED_FACTS.md`. If a fact differs from the plan, stop and report.
4. **Approval gate before any Azure resource or permission change:** show `tools/deploy_free.sh whatif` output, resource list and expected cost. Wait for an explicit "approved". Code-only redeploys (`app`, `worker`) need no approval. Removing the retired Graph write roles (`revoke-graph-writes`), switching agent provisioning on or changing its role list (`provisioning … on`) and switching the agent TAP on (`tap … on`), privileged rows on (`privileged … on`) and agent offboarding on (`offboarding … on`, Entra steps only) are security changes: dry run first, then only with `--approved-by`. Switching them off (`provisioning … off`, `tap … off`, `privileged … off`, `offboarding … off`) is always allowed; removing their rights needs approval.
5. **The agent never approves.** Writes exist only in `GraphDirectoryWriter` (POST users, groups, groups/{id}/members/$ref, and — agent TAP only — users/{id}/authentication/temporaryAccessPassMethods) and `ArmRoleAssignmentWriter` (one PUT of a role assignment), held by the worker only when `AGENT_PROVISIONING` / `AGENT_ROLE_ASSIGNMENT` / `AGENT_TAP` are on, and used only at With ID Team / With Role Team after both current approvals (re-checked before every write; reads before every write). No update, delete, licence or guest invite call; the one TAP call is a create for a user the agent created in the same request. Otherwise only Graph `checkMemberGroups` (read action), Azure OpenAI chat completions and the optional `sendMail` / ADO calls. Approvals only from the named Owner, then a Security member who is not the Owner approver; v1.1 (F3): in Prod, anything above Read also needs an Approved ProdWrite escalation from a ProdApprover (not the requester, not an earlier approver), bound to the request revision and scope (`ProdGuard`, checked at every grant point). v1.1 (F5, Gokul's written approval 30 Oct 2026): offboarding update/delete/revoke calls, worker only, behind `AGENT_OFFBOARDING` (off), only in `GraphOffboardingWriter` (POST revokeSignInSessions, DELETE a TAP method, DELETE members/{id}/$ref, PATCH accountEnabled=false, DELETE user only with `OFFBOARD_DELETE_USER`) and `ArmRoleAssignmentRemover` (DELETE one role assignment, read first: the offboarded user's own, principal type User), only for a plan a person confirmed (a second person in a production tenant; a tenant never marked counts as production), only for the project's own people in a project that names the agent's tenant (a directory-role holder is left to people), every step read first. Never skip a stage, never auto-approve. The AI model never decides or writes. Rows flagged privileged only with `AGENT_PRIVILEGED`; never Owner, Contributor, User Access Administrator, Role Based Access Control Administrator, Reservations Administrator or Key Vault Data Access Administrator (`BuiltInRoles.NeverByAgent`, refused in code and in the RBAC condition).
6. **TAP rules.** The app never receives, stores, logs or prompts a Temporary Access Pass; it records only issued time, expiry, one-time flag and issued-by. One exception, the agent TAP (Gokul, 22 Oct 2026, off until approved): the worker creates a one-time TAP for an account it has just created and sends it once, with the initial password and the MFA steps, v1.1 F2 (30 Oct 2026): only to the people inventory's EnterpriseEmail of that account, equal to its Entra mail or UPN (`TapRecipient`; empty, guest, personal domain, manager, AlternateEmail or mismatch → no mail, *TAP recipient mismatch* escalation), one recipient, no Cc/Bcc, **never redirected** (also in test), via Graph `sendMail` from `TAP_MAIL_SENDER` (`IDirectMail`; `Application Mail.Send` scoped by Exchange RBAC for Applications, F81). Both live only in memory (`Secret`, prints `******`) and in that mail; no copy is stored (audit: user id, masked recipient, time, expiry, correlation id); any failure leaves the pass to the ID team. Root cause of the old behaviour: `docs/ROOT_CAUSE.md`. Mask secrets/TAP as `******` before logs, ADO, mail and prompts (`SecretMasker`). Never paste or log a TAP, password or connection string in chat or docs either.
7. **No secrets or real data** in source, prompts, logs or examples. Sample data is labelled `SAMPLE`. Cosmos connection string lives only in SWA app settings; the worker uses managed identity. Never record personal user ids in docs.
8. **Evidence only.** Never say deployed/working without running it and showing output. Separate facts from assumptions.
9. Ask once per phase, only for blocking choices. Routine reversible coding proceeds.
10. Tenant separation (21 Oct 2026): one project = one Entra tenant (e.g. Vestacy, PEST). The agent reads and writes Entra/Azure only for projects in its own tenant (`AGENT_TENANT_ID`); for another tenant the teams work there and the checks say so. `APP_ENVIRONMENT` = pilot|dev|test|prod; `NOTIFY_REDIRECT_TO` (one test mailbox for every mail) is refused in prod. Real workbook data (group classification, response documents) never goes into git: `tools/import_workbook.py` writes to `.local/` and Cosmos. The live app holds the real tenants only (22 Oct 2026): SAMPLE data is for tests and local runs (`deploy_free.sh app` seeds it only with `SEED_SAMPLE=1`; `seed_sample_data.py --remove-sample` clears it). The request form offers tenant, environment, resource and access level as dropdowns from the mapping sheet only; the Enterprise ID is a mail address.
11. `ALLOW_PAID_SERVICES=false` by default; startup throws if a paid provider is selected while it is false. `ALLOW_UNVERIFIED_ENTRA=true` only with `PILOT_LOCAL_DEV=true`. The worker refuses the retired `ENTRA_AUTO_ASSIGN` / `ENTRA_PROVISION_JOINERS` / `ENTRA_AUTO_CREATE_PACKAGES` settings. `AGENT_PROVISIONING` / `AGENT_ROLE_ASSIGNMENT` / `AGENT_TAP` / `AGENT_PRIVILEGED` / `AGENT_OFFBOARDING` / `OFFBOARD_DELETE_USER` / `EXTERNAL_UPLOAD_API_ENABLED` default false (Bicep and app settings; `OFFBOARD_SUBSCRIPTIONS` empty = every subscription the worker can list); the role allow-lists are `ROLE_ASSIGN_ALLOWED_ROLES` / `ROLE_ASSIGN_SCOPES`; `AGENT_TAP_LIFETIME_MINUTES` (default 480) stays within the tenant's TAP policy.

## Security rules for API code
- Identity comes **only** from `x-ms-client-principal`. Ignore any user/project field in the body. The named Owner is matched on the principal's sign-in name (`userDetails`).
- Look up `userAccess` by the principal's `userId`, and by its sign-in name (`signin:<name>`, same normalisation as the named-Owner match; a principal whose id starts with `signin:` gets nothing). Deny by default (404 for a project the caller has no role in, 403 for a missing permission). Filter every query by the authorised `projectId`.
- Permissions by role: Requester submit/resubmit; Owner decide at the Owner stage (named Owner only); Security decide at the Security stage (not the Owner approver), issues, reports; IdTeam / RoleTeam their tasks; PMO edit the mapping sheet, reports; Operator issues, reports, recover runs.
- Only the agent (`WorkflowAgent`) moves a request between stages; teams and approvers submit inputs that it validates. Idempotency key = request id + step.
- ETag optimistic concurrency on every update.
- Request text is untrusted: injected instructions or "already approved" claims become findings, never actions.
- The ID-team report endpoint rejects any body that carries a pass value (`RejectPassInBody`); notes and justification are masked.
- Contact inventory (`GET/PUT projects/{id}/contacts`): read by every role, saved by PMO and Operators only, If-Match; every entry must be a mail address; Security, ID team and role assignment team never empty. The addresses only route mail: approval rights stay in `userAccess`.
