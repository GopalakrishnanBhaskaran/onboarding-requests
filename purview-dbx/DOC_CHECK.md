## Where the docs differ from the plan

| # | Plan said | Docs say | What we do |
|---|---|---|---|
| D1 | Windows VM SHIR, register with Purview | The IR support table lists **Azure IR, Managed VNet IR (v2) and Kubernetes SHIR** for *Azure Databricks Unity Catalog*. The Windows SHIR column is **empty** for this source. | Kubernetes SHIR on one Linux VM (8 vCPU, 32 GB, 80 GB disk minimum) in the transit VNet. Alternative: Managed VNet IR v2 (no VM), but the two pages disagree on managed private endpoints (D9). |
| D2 | Front-end PE on the existing workspace | Front-end Private Link needs **Premium + VNet injection + secure cluster connectivity**. | If discovery shows a managed VNet, migrate **in place** (documented, no recreate): terminate all clusters and jobs first; NSG + new VNet with NAT gateway + workspace template update (`apiVersion 2026-01-01`, `customVirtualNetworkId`, subnet names). Keep public access **Enabled** during the move. |
| D3 | `browser_authentication` PE | Only needed for **browser SSO over the private path**. Databricks recommends hosting it on a separate, dedicated "web auth" workspace (one per region and DNS zone). | Skip. Your browser stays on the public path, filtered by the IP access list. The SHIR uses tokens, not browser SSO. |
| D4 | "Back-end private, NoAzureDatabricksRules" | `NoAzureDatabricksRules` belongs to **back-end** (classic compute) Private Link. The hybrid front-end model (public access on + IP lists) uses **AllRules**. Back-end PL is independent and not needed by Purview. | Keep `AllRules`, no back-end PE (less risk: a wrong back-end setup stops clusters from starting). Optional later. |
| D5 | Purview PEs account / portal / ingestion; firewall "allow my IP" | **Portal** PE serves only the **classic** portal (web.purview.azure.com). The new portal uses a **platform** PE (tenant-wide; ADF, Azure ML and Synapse connections are not supported with it). Purview firewall options: *Enabled from all networks*, *Disabled for ingestion only (preview)*, *Disabled from all networks*. **No IP allow list.** | Account PE + ingestion PEs (blob, queue; Event Hubs only if managed Event Hubs is on). No portal PE, no platform PE. Firewall: *Disabled for ingestion only* after the scans pass (portal and API stay public with Entra sign-in; scan traffic private). |
| D6 | Workspace storage firewall: allow my IP | Enabling it **blocks all public access** (no IP rule), needs an access connector outside the managed RG plus `dfs` and `blob` PEs, and **deletes the access connector in the managed RG — "can't be undone"**; external locations using it break until remapped. Cloud Fetch clients (the SHIR) then need their own PEs. | Skip (not reversible, not needed for the scan). Purview's known limit: results over 1 MB need access to the workspace storage; our table is small. |
| D7 | Workspace IP access list | Still supported (Premium). Databricks now **recommends account-level context-based ingress** as the primary control; both are enforced together. Whether IP lists filter **private-endpoint** traffic is **not stated** on the pages read. | Use the workspace IP list as asked. PE behaviour: **UNVERIFIED** until wave 3 proves it (SHIR test connection succeeds while your IP is the only allowed one). |
| D8 | Front-end PE in the Databricks VNet; DNS zones linked to both VNets; peering | Front-end PEs go in the **transit VNet** (where clients are). | PE in the transit VNet next to the SHIR, so **peering is not needed**. Do **not** link `privatelink.azuredatabricks.net` to the workspace VNet without peering: the clusters would resolve the workspace URL to an IP they cannot reach. |
| D9 | — | Connector page: Managed VNet IR is supported "however, **Managed Private Endpoint isn't supported** in this case". IR table: "✓ (v2 only, **including managed private endpoint**)". | Conflict → the Managed VNet IR option is **UNVERIFIED**. |
| D10 | — | New VNets created with API versions after 31 Mar 2026 get **private subnets** (no default outbound). The Kubernetes SHIR must reach `mcr.microsoft.com`, `*.data.mcr.microsoft.com` and `*.compute.governance.azure.com` (wildcard, **no private endpoint**). | NAT gateway on the SHIR subnet. VNet injection template also uses a NAT gateway. |
| D11 | Test via `Test-NetConnection` on Windows | Linux SHIR | Same checks with `nslookup`, `nc -zv <host> 443` and `curl` on the VM through `az vm run-command` (no inbound port, no Bastion). |
